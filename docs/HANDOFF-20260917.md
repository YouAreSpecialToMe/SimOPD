## 1. 交付物在哪

两个 Hugging Face 公开仓库。**代码在本分支,数据和权重在 HF**,不要指望在 git 里找到它们。

### 1.1 `Jerrycool/opd-ckpt`(模型仓库,865.2 GiB / 668 个文件)

```
resume/<arm>_s0/global_step_<n>/     268.1 GiB   10 条臂,**带优化器状态的完整存档**
eval/<arm>_s0/global_step_<n>/       597.1 GiB   24 条臂,只有 hf 权重
MANIFEST.tsv                                     668 行:路径 + 字节数
README.md
```

分工是按"接下来要拿它干什么"切的,不是按重要性:

- `resume/` 是**还要接着训**的 10 条臂的最后一个存档。带 `actor/`、优化器状态、
  `data.pt`,verl 能直接 `resume_mode=resume_path` 续上。体积大是因为优化器状态跟权重
  同量级。
- `eval/` 是**只需要补评测**的 24 条臂的各个步。只导出了 `actor/huggingface/`,
  因为评测只加载权重,不需要优化器。
- 两边有重叠:一条既没训完、又没评完的臂,在 `resume/` 里有它的最后一个存档,在 `eval/`
  里有它此前的各个步。

**已经训练完 + 评测齐全的 5 条臂没有传权重**(`c2_quantile_budget_corr`、`c4_hq`、
`c4_pi_tail_budget_corr`、`c4_state`、`vanilla_corr`)—— 它们的产物和读数都在数据集仓库里,
权重对完成剩余工作没有用。要复现的话得重训。

### 1.2 `Jerrycool/opd`(数据集仓库,13.55 GiB / 186 个文件)

```

assets/gkd_offpolicy.parquet.dry   0.3 MiB   a5 的成员集(SIMOPD_A5_KEYS)

```

训练侧产物打了包,评测 parquet 没打 —— 前者 24132 个小文件逐个传会撞上 HF 每账号

包内结构:

```

  traj/                    逐步轨迹
    light.jsonl              每步一行的轻量记录
    ids_<step>.parquet       每步 rollout 的无损 token id
    summary_<step>.parquet   每 25 步的每序列摘要(含教师列 tch_lp_* / tch_top1_*)

    div/tok_step<s>_rank<n>_<i>.parquet

  metrics/launch_<ts>.jsonl 逐步全指标,141–191 列/臂

  run_manifest.json / simopd_fingerprint.txt / simopd_stop_contract.txt
```

## 2. 硬件前提

这一轮跑在 **8×H100(80 GB)/节点**的 Slurm 集群上,EXCLUSIVE 调度(一个作业独占整节点)。

关键的架构约束:**一条 lane = 2 张 GPU**(`GPUS_PER_RUN=2`,见 `deploy/dsw/run_parallel.sh:61`)。
学生 1.7B + 教师 4B 的 vLLM 实例要共存在这两张卡上。所以:

- 1 个节点 = 8 张卡 = **4 条 lane**,一次能并行跑 4 条臂。
- `GPUS_PER_RUN` 不是随便调的旋钮。改成 1 装不下教师,改成 4 会让每节点只剩 2 条 lane、
  吞吐减半而单条不会更快(单条 lane 的瓶颈是 rollout,不是显存带宽)。

更小的卡(A100 40 G / L40S)没有试过。响应上限是 16384 token,KV cache 的占用在长序列段
很吃紧 —— Mode A 的现象本身就是"长度从 1k 涨到 16k",跑到后期几乎必然逼近上限。

**不需要多节点通信**。每条 lane 是独立的单机 Ray 作业,节点之间零交互。所以有几个节点就
能并行几个 ×4 条臂,线性扩展,没有 all-reduce 的规模上限。

## 4. 配置:`simopd_env.sh`

从 `simopd_env.example.sh` 复制。这一个文件就是全部的机器相关配置 —— 仓库里的脚本几乎
都在开头 `. ./simopd_env.sh`。**它在 `.gitignore` 里,密钥只放这份,不要提交。**

| 变量 | 作用 | 备注 |
|---|---|---|
| `OPD` | 工作区顶层 | 下面放代码、数据、日志 |
| `SIMOPD_ROOT` | 本仓库 checkout | 含 `verl/` 子克隆 |
| `SIMOPD_STORE` | 数据根 | ckpt / traj / evals / 队列 / 闸门都在这下面 |
| `OPD_LOGS` | Slurm 日志 | `%x-%j.out` 落这里 |
| `CKPT_ROOT` | `$SIMOPD_STORE/ckpt` | |
| `DATA_DIR` | `$SIMOPD_STORE/simopd_math` | MATH 数据 **和 A 轴的 gkd 缓存** |
| `SIMOPD_EVAL_ROOT` | `$SIMOPD_STORE/evals` | 评测 parquet |
| `SBATCH_PARTITION` | 分区 | Slurm 原生变量,**必填** |
| `SBATCH_OUTPUT`/`ERROR` | 日志路径 | Slurm 原生变量 |
| `SLURM_EXCLUDE_NODES` | 排除名单 | 没有原生变量,由提交方转成 `--exclude` |
| `SIMOPD_SUITE_K` | 评测采样数 | **必须是 8**,理由见 §8.1 |
| `WANDB_MODE` | `offline` | 计算节点不出网 |
| `HF_HUB_OFFLINE` | `1` | 要下载时临时置 0 |

> **为什么分区不写在 `#SBATCH` 里:** sbatch 的指令行**不展开 shell 变量**。写
> `#SBATCH --output=$OPD_LOGS/%x-%j.out` 不会得到你想要的路径,只会在当前目录建出一个
> 名叫 `$OPD_LOGS` 的目录。所以凡是随机器变的东西一律走 Slurm 原生的 `SBATCH_*` 输入
> 环境变量(`man sbatch` 的 INPUT ENVIRONMENT VARIABLES 一节),export 了就生效。
> 排除名单是唯一的例外 —— Slurm **没有** `SBATCH_EXCLUDE`,所以由
> `campaign_scheduler.sh` / `night_window.sh` 读 `SLURM_EXCLUDE_NODES` 后用
> `--exclude` 传。手工 sbatch 时自己带上。

```bash
sbatch ${SLURM_EXCLUDE_NODES:+--exclude="$SLURM_EXCLUDE_NODES"} slurm/retrain_a_axis_gate.sbatch
```

> `rehearse_a_axis.sh` 里靠 `KNOB=${ARM%_n0}; KNOB=${KNOB%_corr}` 剥掉后缀 —— 这个修复

> 没有执行**(误 PASS)。改完之后判据只会更严,不会更松。

### 5.4 摆放取回的 checkpoint —— 用脚本,别手工 cp

一条臂的运行目录 `$CKPT_ROOT/simopd/<arm>_s0/` 里**同时**放着两样东西,而它们被拆到了
两个仓库:

```
$CKPT_ROOT/simopd/<arm>_s0/
    traj/ val_gen/ metrics/ manifest/          ┐
    run_manifest.json                          │ 来自 Jerrycool/opd
    simopd_fingerprint.txt                     │ (runs/<arm>_s0.tar.zst)
    simopd_stop_contract.txt                   │
    latest_checkpointed_iteration.txt          ┘
    global_step_<n>/                           ← 来自 Jerrycool/opd-ckpt
```

**两边必须合回同一个目录,少一边都跑不起来:**

- 没有 `simopd_stop_contract.txt`,`eval_offline.py` 的 `resolve_stop_contract()` 从
  `--model` 路径往上找不到停止契约,评测口径就和产出这批数据时不一致(它是从模型路径
  往上走几级去找 `<run_dir>/simopd_stop_contract.txt` 的)。
- 没有 `latest_checkpointed_iteration.txt`,`run_opd_baseline.sh` 会当作**从 0 开始**。
  好消息是这个文件在 runs 包里,解包就有,不用自己重建。

**还有一处形状差异,直接 `cp` 会踩:**

```
opd-ckpt/resume/<arm>/global_step_N/   verl 原样布局(actor/ + actor/huggingface/ + data.pt)
opd-ckpt/eval/<arm>/global_step_N/     **平铺**的 hf 权重(config.json / model.safetensors / …)
```

而评测入口写死在 `<step>/actor/huggingface`(`deploy/dsw/eval_worker_exp.sh:93` ——
`actor/` 是 FSDP 分片,vLLM 读不了)。所以 `eval/` 那一份**必须重新嵌套**进
`actor/huggingface/`,平铺着放评测端是找不到的。

这三件事由一个脚本做完:

```bash
huggingface-cli download Jerrycool/opd-ckpt              --local-dir dl_ckpt
huggingface-cli download Jerrycool/opd --repo-type dataset --local-dir dl_data
. ./simopd_env.sh
bash scripts/assemble_handoff.sh dl_ckpt dl_data
```

它解包训练产物、搬续训存档、把评测权重重新嵌套、把 A 轴的离策缓存放到 `$DATA_DIR`,
最后逐臂自检并打印:

```
  ok a4_dagger_anneal_n0_s0       latest=175  可评步数  4  可续档 1
  -- c4_hq_s0                     训练完 + 评测齐全,故意未传权重(读数在数据集里)
  ...
  可开工 24 条 | 已完结 5 条 | 不完整 0 条
```

幂等,重跑只会跳过;`FORCE=1` 强制重做。**自检不过就不要往下走** —— 它比对的是
"opd-ckpt 里出现过的臂,权重是不是都摆到位了",不通过就是下载或摆放出了问题。

> 那 5 条报 `--` 的臂(`c2_quantile_budget_corr`、`c4_hq`、`c4_pi_tail_budget_corr`、
> `c4_state`、`vanilla_corr`)是**故意**不传权重的:训练完 + 评测齐全,权重对完成剩余
> 工作没有用。读数在数据集仓库里。要复现它们得重训。

## 6. 在跑什么(看懂剩下几节所必需的最小背景)

### 6.1 现象

学生 `Qwen3-1.7B-Base` 向教师 `Qwen3-4B-Instruct-2507` 做在线策略蒸馏,任务 MATH。
**Mode A 长度塌缩**:响应长度从 1k 一路涨到 16k,截断率逼近 100%。这是被研究的对象,
不是需要消除的开销 —— 看到长度爆炸不要去"修"它。

### 6.2 终止符语义错配

学生停在 `<|endoftext|>`(151643),教师停在 `<|im_end|>`(151645)。逐 token 的 KL 在比

### 8.1 网格与口径

一"格" = 一个 (臂, 步) 组合。`--grid light`:

## 10. 这一轮踩过的坑

按"从代码本身看不出来"的程度排。每条都给了修复位置。

### 10.1 `USER: unbound variable` —— 三个晚上零产出

Slurm 的批处理环境**没有 `USER`**,而脚本开了 `set -u`。
cron → 看门狗 → 守卫 → 调度器 → sbatch 这条链一路都不传 `USER`,于是作业一起来就死。
表现是窗口照常打开、作业照常提交,然后什么都没有。

**修复**:`ME=$(id -un)`,不依赖环境。见 `slurm/window_watchdog.sh:21`。

同源的旧事故:看门狗查不到守卫 → 每 5 分钟多起一个守卫 → 每个守卫起一个调度器 →
每个调度器 `squeue -u ""` 查不到作业、以为 0/4 → 各自投满 4 个,超投到 7 个作业。

### 10.2 看门狗的三类误杀

掉队检测(作业还活着但卡没跑满)本身是对的 —— 这一轮有两次静默空烧整夜。但判据一开始太
粗,连续误杀了三类健康作业:

1. **杀了 A 轴预演门。** 预演门是四条彩排并行,一条跑完就放一条的卡,天然"空卡越来越多"。
   跑到 3/4 PASS 时被当成掉队杀掉。
   **修复**:只对 `simopd-lane*` 作业做掉队检测。
2. **杀了正常收尾的 lane 作业。** 一条 lane 把分给它的臂全跑完就打印 `LANE_DONE` 退出,
   它那两张卡是**正常**释放的。6697 就这么被杀,三条还在训练的 lane(含每步 18 分钟的
   `c5_union_rkl`)陪葬回退 25 步。
   **修复**:数**还没打 `LANE_DONE` 的** lane,不是数派了几条。
3. **窗口末尾的误杀是纯损失。** 光 vLLM 起模型就 10–15 分钟,再加回退到上一个存档,
   末尾杀掉的作业没有时间挽回;而 lane 换臂期间本来就短暂放卡,恰好长得像掉队。
   **修复**:剩余 < 45 分钟一律不判。

### 10.3 把作业时限削成 1 分钟

看门狗会把跑过窗口末端的作业时限**削**到窗口末端(Slurm 只允许降不允许升)。但它原来对
**PENDING** 的作业也削 —— 而 PENDING 作业的 `StartTime` 是 Slurm 的**预估**开跑时刻,
不是事实。一个排队作业被预估到 15:28 才开跑,于是算出 left = 15:30 − 15:28 = 1 分钟,
时限被削成 `0:01:00`;它 10:35 真正起来,**80 秒后**就 `CANCELLED DUE TO TIME LIMIT`。

**修复**:只削 `JobState=RUNNING` 的。排队的等它跑起来下一轮(最多 5 分钟后)再按真实
`StartTime` 削一次就是精确的。见 `slurm/window_watchdog.sh:115`。

**注意**:降下去就再也放不回去。削错了只能 `scancel` 重投。

### 10.4 调度器读过期的临时开窗值

`force_window_until` 是**临时**开窗的覆盖值,过期就必须当它不存在。守卫有 `now < fu` 的
守卫条件,调度器**没有** —— 于是它读到一个早已过期的时刻,算出"距窗口结束还剩 −990 分钟",
连续 76 分钟拒绝派工。

**修复**:调度器加同样的过期判断,并回落到 `WINDOW_END_EPOCH` → 当天的 `WEND_HHMM`。

### 10.5 装箱贪心导致节点空着

调度器原来是贪心装箱:能塞多少臂就往一个作业里塞多少。名册见底时,剩下的臂全被塞进一个
作业,其余节点空着。

**修复**:按**还空着的节点数摊平** —— `cap = ceil(n_todo / free_jobs)`。

### 10.6 节点本地 SSD 被占满

Ray 的 spill 落在计算节点的 `/tmp`。某个节点的本地盘 100% 满,七条臂同时 ENOSPC 而死;
扫掉我们自己的残留 `ray_lane*` 目录只回收 5 G —— 占盘的不是我们。

**修复**:`retrain_lane_node.sbatch` 加了开工前的清扫(跳过还有活进程的目录)+ 可用空间
预检(< 200 G 直接 FATAL 退出)。这把"跑一半炸"变成"立刻失败",但躲开还得靠
`SLURM_EXCLUDE_NODES`。

### 10.7 `env` 解析到一个不可执行的文件

重新拉起 lane 时用 `env VAR=x cmd` 的写法,`env` 被解析成了 `~/.local/bin/env`(不可执行)。
**修复**:用 `bash -c`。

### 10.8 `ROCR_VISIBLE_DEVICES` 和 `CUDA_VISIBLE_DEVICES` 打架

Slurm 会注入 `ROCR_VISIBLE_DEVICES`,和我们设的 `CUDA_VISIBLE_DEVICES` 冲突,vLLM 看到的
卡号不对。**修复**:`unset` 掉。见 `deploy/dsw/eval_worker_exp.sh:34` 的
`env -u CUDA_VISIBLE_DEVICES -u ROCR_VISIBLE_DEVICES`。

### 10.9 Ray 的 socket 路径长度上限

Unix domain socket 路径有 108 字节上限,`RAY_TMPDIR` 放太深会让 Ray 起不来,报错信息和
路径长度毫无关系。保持 `$RAY_TMPDIR` 短。

### 10.10 端口 TOCROU 竞争

`c5_union_rkl` 曾以 `DistNetworkError ... code -98`(address in use)失败:两条 lane
探测到同一个空闲端口后才各自去绑。重投即可,但要知道这个错不是配置问题。

### 10.11 教师列切片错位

`traj_dump.py` 读教师块时用了 `[P:P+L]`,把响应 token j 对到了教师对**下一个** token 的
分布。后果是安静的:采样列查不到就记 NaN,`tch_lp_nan` 占到响应长度的约 57%,
`tch_lp_last` 恒 NaN,`summary` 的 `dl_*` 全是拿错列算出来的。

正确的是 `[P-1:P+L-1]`。实测(`vanilla_corr` step 25,24 条序列):

```
resp[i+1] == tch_top1_id[i]   0.7620    <- 真正的对齐
resp[i]   == tch_top1_id[i]   0.0463
```

**训练不受影响** —— loss 走 verl 自己的教师打分,不经过归档层。只有读数错。
`ch-dev` 已在 09-09 移植了这个修复。不变量:`KEEP_SAMPLED=1` 时 `tch_lp_nan` 必须为 **0**,
非零就是错位,不是"接近 0"。

**本仓库数据集里的数据全部来自修复后的重跑**,抽查 `tch_lp_nan` 为 0。

### 10.12 评测 refill 的活锁

## 11. 已知缺口

1. **部分步在 `metrics/launch_*.jsonl` 中缺失**,出现在作业被取消或到达时限的时刻附近。
2. **同一步可能有多条记录**(从存档续跑造成的重叠),按文件时间取最近一次。
3. 未完成的臂全部经历过多次续跑,`launch_*.jsonl` 文件数最多的有 13 个。
4. 实验跟踪全程 offline,**没有在线曲线**;`metrics/` 就是可得的全部指标记录。
5. 非锚点步(25/50/150)不跑 AIME,**凑不出五基准加权 composite** —— 这是 light 网格的
   设计,不是缺失。
6. **评测是 avg@8 而不是协议的 avg@32**,方差比协议口径大。见 §8.1。
7. `c5_union_rkl` 的存档节奏问题没解决(§7.3)。
8. **`verdict.py` 的 c2 基线映射,本分支与 `ch-dev` 判断相反。** `ch-dev`(09-05 的全项目
   审查)给 `c2_qb_fixed8_corr` / `c2_qb_perseq_corr` 配了
   `BASE_OVERRIDES -> c2_quantile_budget_corr`;这一轮在集群上的判断是"c2 的两级梯子不给
   override,按 §2.2 的基座规则判决对象就是 `--base`"。**本分支采用了 `ch-dev` 的版本**
   (它更晚、且出自一次完整审查),但这是一个尚未裁定的分歧,出读数前先确认要哪一个。
9. `deploy/dlc/eval_worker_exp.sh`(`ch-dev`,230 行)和 `deploy/dsw/eval_worker_exp.sh`
   (本分支,135 行)是两边独立重写的两个版本,没有共同祖先。本分支两个都在,用的是
   `dsw` 那个(`retrain_eval_farm.sbatch` 调它)。**需要有人裁定合并成一个。**
